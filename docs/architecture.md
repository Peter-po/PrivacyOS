# PrivacyOS 安全架构

## 威胁模型

初期关注普通应用越权访问其他应用数据、默认网络流量泄露使用信息、设备丢失后的离线数据读取，以及系统镜像和更新被篡改。信任边界涵盖设备硬件信任根、启动加载器、系统签名和更新基础设施、Android 内核及特权服务。供应链攻陷、未修复的硬件漏洞和具备系统级执行能力的攻击者需要单独建模和验证。

## 安全边界与验证

| 层级 | 设计要求 | 验证方式 |
| --- | --- | --- |
| 启动与设备信任 | 在支持的设备上使用锁定的启动加载器、AVB 验证和回滚保护。按设备记录允许的信任根。 | 读取启动状态作为冒烟检查，在实验设备上独立验证签名拒绝和回滚保护。 |
| 内核、应用与服务 | 保持应用 UID 隔离和 SELinux 强制模式。审查新增的系统服务、权限和策略例外。 | 执行 SELinux 状态检查，为新增权限设计负向测试，并按设备运行相关 Android 兼容性测试。 |
| 用户数据 | 维持文件级加密与凭据保护。分别评估首次解锁前和首次解锁后的可访问数据。 | 在支持的设备上验证锁屏、重启和个人资料隔离相关行为。 |
| 应用与系统联网 | 记录默认联网的系统组件、目的地和数据用途。评估用户可控制的应用联网权限。 | 在隔离测试网络上采集流量，比较首次启动、空闲和执行操作时的请求。 |
| 构建与更新 | 记录 AOSP manifest、工具链和下游补丁版本。发行密钥与开发密钥分离，更新包必须经授权密钥签名。 | 审查构建输入和签名产物，在测试设备上验证更新、错误签名拒绝和回滚策略。 |

## 开发阶段

先构建指定 AOSP 基线并固定源码版本，在 Cuttlefish 上验证启动与基础功能。开发镜像可使用 `userdebug`。进入设备验证阶段后，使用独立的 `user` 镜像检查 SELinux 强制模式、调试属性及锁定启动状态，并记录机型、构建版本和验证结果。真实设备的硬件信任根、设备加密和更新行为需要逐机型验证。

将每项下游改动关联到威胁模型、测试和维护责任。对外发布前，需要明确支持的设备和补丁生命周期，验证发布签名与更新流程，并记录已知限制。

参考 [Android 应用沙箱](https://source.android.com/docs/security/app-sandbox)、[SELinux](https://source.android.com/docs/security/features/selinux)、[Android Verified Boot](https://source.android.com/docs/security/features/verifiedboot) 和 [文件级加密](https://source.android.com/docs/security/features/encryption/file-based)。
